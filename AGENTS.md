# AGENTS.md — Инструкции для Codex

## 1. Контекст проекта

`price-tracker` — событийно-ориентированная система мониторинга цен игр Steam на Java и Spring Boot.

- Соблюдай стандарты кода, документации и тестирования из [CLAUDE.md](CLAUDE.md).
- Используй [описание архитектуры](docs/architecture.md) и проверяй архитектурные предположения по актуальному коду.
- Явно отмечай, какие возможности уже работают, какие реализованы частично и какие пока запланированы.

## 2. Работа над задачами

- Работай в рамках назначенной GitHub Issue и её критериев приёмки. Согласовывай соседние Issues и несвязанные улучшения отдельно.
- Для нетривиальной задачи предложи план до правок. Укажи затрагиваемые компоненты и способ проверки.
- Если запрошены только исследование, планирование или ревью, не изменяй файлы.
- При существенной неоднозначности опиши варианты и согласуй решение до архитектурных изменений.
- Предпочитай минимальные изменения в рамках существующей архитектуры. Обосновывай новые зависимости и абстракции.

## 3. Git и параллельная разработка

- Перед правками проверь текущую ветку, базовый коммит, `git worktree list` и `git status --short --untracked-files=all`.
- Для каждой GitHub Issue используй отдельную ветку. При начале новой задачи создавай её от актуальной целевой ветки. При продолжении работы используй уже существующую ветку задачи. Не создавай повторно ветку для той же Issue. Для параллельной работы используй отдельный worktree или изолированный локальный клон. Не изменяй ветки и рабочие каталоги других задач.
- Сохраняй чужие изменения, включая staged и untracked-файлы. Не перезаписывай, не удаляй и не убирай их в stash. Если пересечение мешает безопасно продолжить, сообщи о нём и согласуй дальнейшие действия.
- Не выполняй `git reset --hard`, `git clean`, force push, переписывание истории и другие разрушительные операции без явного разрешения.
- Включай в коммит только файлы задачи. Исключай посторонние локальные настройки и временные артефакты.
- Выполняй merge конкретного PR только после отдельного явного разрешения разработчика. Успешный CI, одобрение PR и разрешение на push сами по себе такого разрешения не дают. Не включай auto-merge.

## 4. Реализация и тестирование

- Соблюдай стиль кода и границы ответственности модулей. Переиспользуй существующую реализацию и сохраняй текущее поведение, кроме изменений, предусмотренных задачей.
- При изменении поведения добавляй или обновляй тесты, если имеющееся покрытие не проверяет новое поведение. Применяй Red → Green → Refactor, если этот подход согласован для задачи.
- Не ослабляй тесты и не меняй ожидаемые результаты только ради успешной сборки.
- Запускай тесты и проверки, относящиеся к задаче. Перед публикацией PR запусти полную сборку, если она применима к изменениям.
- Перед передачей результата сверь критерии приёмки, проверь `git status --short`, `git diff --check` и итоговый diff, включая содержимое новых файлов.
- Не изменяй бизнес-логику в задачах, ограниченных документацией или конфигурацией.

## 5. Pull Request и Code Review

- Пиши заголовки и описания PR на русском языке. Сохраняй оригинальные имена классов, методов, переменных, библиотек, команд и технические термины.
- Пиши сообщения коммитов на английском языке. Следуй принятому в репозитории формату.
- Свяжи PR с GitHub Issue. В описании укажи цель, причину проблемы, выполненные изменения, результаты проверок и известные ограничения.
- Перед публикацией проверь полный diff относительно целевой ветки и состав новых и untracked-файлов.
- Если согласованный этап предусматривает предварительное ревью или отдельное разрешение, дождись его перед commit, push или созданием PR.
- В замечании ревью укажи файл и строку, условия проявления проблемы и её последствия. Перед исправлением сверяй замечания с кодом и требованиями задачи.
- После исправлений повтори затронутые проверки и сообщи, какие замечания устранены и какие остаются открытыми.

## 6. Безопасность и инфраструктура

- Не добавляй реальные пароли, токены, ключи API и другие секреты в репозиторий. Не раскрывай их в логах, документации, ответах, отчётах и PR. В примерах используй безопасные заглушки.
- Не изменяй production-инфраструктуру и внешние ресурсы без явного разрешения. Согласовывай разрушительные операции с базами данных.
- Изменяй настройки Kafka, PostgreSQL, Kubernetes и Docker только в рамках текущей задачи.

## 7. Документация

- Обновляй затронутую документацию при изменении поведения, архитектуры или порядка запуска.
- Ссылайся на действующие стандарты и общие инструкции из их исходных файлов.
- Если документация расходится с реализацией, укажи, где именно обнаружено расхождение.

## 8. Отчёт о выполненной работе

- Опиши, что изменено и почему. Перечисли созданные, изменённые и удалённые файлы.
- Укажи выполненные критерии приёмки и те, которые остались открытыми или непроверенными.
- Приведи фактически выполненные команды и их результаты. Для тестов укажи уровень проверки: unit, integration или end-to-end. Отдельно перечисли пропущенные проверки, причины пропуска и непроверенные сценарии.
- Сообщи об известных рисках, ограничениях и посторонних или untracked-файлах. Укажи, какие из этих файлов относятся к задаче.
- Отделяй подтверждённые факты от предположений. Сообщай об успешном выполнении только тех действий, которые фактически выполнил.
